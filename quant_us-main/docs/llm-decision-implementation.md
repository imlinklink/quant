# LLM深度参与交易决策实施方案

版本 v1.0　日期 2026年9月8日　适用项目 quant_us-main

本文定义下一阶段的开发范围：把 LLM 从一次性的买卖建议，升级为围绕同一份交易计划持续提供研究、复核与退出建议的组件，同时建立对照账本，检验规则、LLM、人工筛选和执行分别如何影响收益。所有买卖仍由用户明确确认，数量及账户风险由程序约束。

本文件是待开发的实施方案。编写本文不代表相关功能已经实现或启用，也不改变现有交易参数、进程与审批配置。首个开发里程碑是完整的对照账本和可追溯交易计划；随后接入结构化决策卡及持仓事件复核。策略盈利能力需要独立验证，工程验收通过不等同于收益提高。

## 一 参考模板的取舍

参考文件为用户提供的《极简交易计划模板.docx》。采用其一页计划和交易前后检查的组织方式，把关键问题保留在用户能快速审阅的一页内；数据、证据和实现细节放在可展开部分。

| 模板内容 | 本系统的处理 |
| --- | --- |
| 标的与动用资金比例 | 展示标的、策略来源、预计数量、资金比例和同产业链暴露，由程序计算 |
| 最大止损比例 | 同时展示初始止损价、价格距离、计划风险金额R、净值占比；计划风险不冒充最大可能损失 |
| 买入理由 | 拆成规则信号、可核实事实、LLM推断，以及最重要的反对证据 |
| 止盈目标或策略 | 按反弹仓与趋势仓分别填写，冻结已批准版本，后续修改保留历史 |
| 极端行情预案 | 写清触发条件、拟议动作、数据缺失处理和通知方式，任何买卖仍需LLM评估和人工确认 |
| 交易前后纪律检查 | 记录有无计划、偏离计划、亏损加仓、拒绝退出、追价与实际成交偏差，形成可复盘事件 |
| 强制24小时冷却、3/5/7仓位框架、连续亏损自动降仓 | 不直接采用为执行规则。含义及适用条件未经本系统验证，先作为可讨论的实验项；自动卖出与当前审批约束冲突，不启用 |

模板中的数字和动作不是用户已批准的系统参数。现有风险预算与新增策略的关闭状态继续保持，本文不扩大自动交易权限。

## 二 现有基础与需要补齐的部分

以下判断来自当前仓库代码，未检查运行中进程是否已加载对应版本。

| 现有组件 | 已有能力 | 本阶段缺口 |
| --- | --- | --- |
| decision_ledger/scan_ledger.py | 抄底扫描、组件分和筛选结果 | 跨策略统一信号标识、规则通过但没有提案的完整记录；周期和版本隔离 |
| decision_ledger/ledger.py | 提案、人工决定及执行事件的JSONL记录 | 事件级幂等、明确时区、完整关联、写入失败可观测性 |
| approval/proposal_store.py | 人工批准、拒绝、过期，以及LLM评估完成门槛 | 绑定计划版本与评估版本；异步LLM回填的独立事件；覆盖建议的理由 |
| execution.py 与 position_registry.py | SQLite订单、累计成交、持仓、部分成交、未知状态及风险预算 | 独立交易周期ID、增量成交经济数据、不可变初始R、成交到归因账本的可靠投递 |
| mutifactor/llm/advisor.py | 买入评估与卖出建议 | 共用结构化输入、来源引用、持仓连续记忆、独立买卖语义与计划差异 |
| decision_ledger/weekly_report.py | 事件数量、建议分布和部分结果统计 | 同一候选集合的四层对照、执行损耗、未交易机会与统计不确定性 |

当前卖出评估复用买入的 allow/delay/block 形状：同一个字段在买卖两侧含义不同。后续需要独立的动作字段和适配器，不能直接把旧数据的 block 统一当成同一种行为。

当前 llm_ready 表示“评估有合法结果”，并不要求模型建议必须为 allow。新方案延续“LLM评估完成，用户最终决定”：模型反对时，用户可以在程序风险约束内选择执行，但必须看到反对依据并记录覆盖理由。模型无结果、过期或格式无效，不能按已完成评估处理。

旧扫描说明仍包含5分钟周期，而当前抄底输入已改成已收盘15分钟。历史结果必须携带周期与策略版本，不能直接拼接统计；缺失字段标为 legacy_unknown，不推测补全。

## 三 权限分工与执行边界

| 参与方 | 职责 | 不具备的权限 |
| --- | --- | --- |
| 规则程序 | 候选信号、行情有效性、价格和风险计算、订单状态及对账 | 不把未获确认的建议转成买卖 |
| LLM | 解释证据、反对证据、交易逻辑变化，提出条件明确的建议 | 不修改账户上限、不直接调用下单接口、不静默改止损或仓位 |
| 用户 | 批准或拒绝具体计划、具体买卖与计划修订 | 确认不跳过程序必需的报价、风险和订单状态核验 |
| 对照评估器 | 只读记录，重放预先定义的假设，评估决策结果 | 不直接反馈修改实盘参数或触发订单 |

计划批准和订单批准是两个概念。可以在页面上用一次点击同时批准当前计划版本及当前具体订单，但不能把批准整份计划解释为未来所有卖出、减仓或加仓的长期授权。确认应绑定账户、标的、买卖方向、数量上限、价格容忍范围、有效期、计划版本和LLM评估ID。

任何实质修订，包括放宽止损、修改目标、延长持有期、转换策略类型，都生成新版本和差异说明，并重新确认。旧批准不能授权新版本。第一阶段不提供亏损摊平、自动加仓或自动分批退出；已有禁止重复买入等约束照常执行。

## 四 一页交易计划

计划顶层保持精简，详细证据放在展开区。以下字段是每笔新交易必须明确的数据，而不是要求用户手工填写全部信息。

| 字段 | 内容与责任 |
| --- | --- |
| 标的与策略 | 代码、方向、dip_buy/donchian/pullback等策略及版本；程序填写 |
| 为什么现在交易 | 规则触发条件、LLM解释、对应证据ID；事实和推断分开 |
| 预期收益来源 | 超卖修复、趋势延续或其他预先定义的逻辑；不得随亏损临时转换 |
| 入场约束 | 下一可交易报价、追价限制、数量和金额上限；程序复核 |
| 风险边界 | 初始止损、每股风险、计划风险R、账户/产业链占用及报价时间 |
| 盈利退出 | 固定目标或趋势跟踪规则，明确是否仅全仓退出 |
| 交易失效 | 结构、事件与时间条件，写成可观察的触发标准 |
| 极端行情预案 | 何时提醒、建议做什么、无法取得LLM结果时怎样呈现阻塞；不自动成交 |
| 主要反对证据 | 至少展示检索范围内最重要的反对事实，或明确尚未取得相关资料 |
| 用户决定 | 批准/拒绝/要求补充；若偏离LLM建议，保存理由 |

一页之外保存：原始行情快照、证据包、计算结果、LLM输入输出、版本链和执行回报。不能以一段可被覆盖的“持仓备注”代替完整交易计划。

## 五 LLM参与的三个时点

### 买入前形成判断

所有策略进入同一评估接口，但问题随策略变化。抄底重点检查下跌是否伴随新的经营恶化信息，突破重点检查新旧催化、事件窗口与追价背景，回调重点检查趋势依据是否仍在。程序提供已完成K线、初始止损、目标和风险；LLM不得自行编造这些数值。

先写入规则候选事件，再异步调用LLM，避免仅保留成功生成提案的样本。无论支持、反对、信息不足、调用失败或用户未操作，都保留同一信号的后续记录。LLM返回后，必须重新核验报价和计划约束，不能按等待前的快照直接执行。

### 持仓中按事件复核

每笔持仓读取已批准计划及最近一次评估，回答“相比上次什么发生了变化”。触发源包括新公告/财报/指引、规则失效、接近风险边界、接近目标、时间条件和每日收盘。接近阈值先沿用明确的程序配置，不由模型临时决定。

同一事件簇、同一计划版本在短时间内只触发一次；多家媒体转述同一公告不能算多条独立确认。无新证据时维持原计划，不因措辞变化频繁生成交易建议。记录数据仍旧或资料不足，不把“未取得新闻”说成“没有风险”。

首阶段复核只更新决策卡或提出需确认的修订，不自动改单。只有形成具体动作、经程序核算并由用户明确确认后，才进入现有执行入口。

### 卖出前解释原计划是否完成或失效

输入必须包含开仓理由、原始风险、目标/跟踪规则、当前保护线、触发原因、已实现与未实现盈亏、新增证据、现有活动订单。LLM区分止损、结构失效、时间退出、目标兑现与趋势退出，不能一律用“公司长期看好”解释继续持有。

硬止损复核使用简短的优先队列，展示“已触发、待评估、待确认、待成交”的真实状态。没有模型结果时显示阻塞并提醒；提案过期或用户拒绝时不自动卖出，保留原计划和风险提示。限价单未成交也不能显示为风险已经解除。

## 六 输入证据与结构化决策卡

证据快照必须区分事件发生时间、来源发布时间、系统取得时间与评估时间。默认使用UTC存储，界面按美东或北京时间展示。回放时只允许读取当时已取得的资料；事后修订的财报数据不能覆盖历史输入。

每条证据保存 evidence_id、来源地址/公告标识、published_at、observed_at、简短摘要、内容哈希和事件簇ID。引用验证先检查来源确实存在于输入包，再检查事实与来源是否一致。来源优先级、报价/新闻/财报有效期由配置明确，不用一个统一TTL覆盖所有资料。

新闻、网页、上传文件和模型输出都属于不可信数据。它们不能改系统提示词、要求泄露凭证、改变审批或直接执行工具。模型仅接收必要的账户汇总，不接收API密钥、完整无关账户信息；研究工具与交易工具分离。

建议采用以下概念结构，由专用schema验证，具体字段名在开发时固定：

```json
{
  "review_id": "review_example",
  "plan_id": "plan_example",
  "plan_version": 1,
  "decision_type": "entry_review",
  "status": "complete",
  "recommendation": "support_execute",
  "proposed_action": "buy",
  "thesis_state": "unchanged",
  "facts": [{"text": "可核实事实", "evidence_ids": ["evidence_example"]}],
  "inferences": [{"text": "基于事实的推断", "evidence_ids": ["evidence_example"]}],
  "counterevidence": [],
  "missing_information": [],
  "plan_change_requested": false,
  "next_review_conditions": ["由程序监测的事件条件"]
}
```

这是结构示意，不是真实交易建议或真实证据。运行时还需补齐 input_snapshot_id、模型/提示词/schema版本、请求与响应时间、有效期、耗时、token和调用成本。

status区分 complete、insufficient_information、failed、stale；推荐区分支持执行、建议暂缓和建议不执行；拟议动作使用买入、持有、减仓、退出、修订计划等独立语义。不得把“数据不足”填成低信心支持。资料不足可以展示，但不计作满足买卖审批的有效评估。

决策卡显示最多三条核心依据和最重要的反对证据，展开后可查看完整输入。模型自报信心只作为原始字段，不标成胜率；如要显示概率，另行定义预测目标、期限和校准验收。

## 七 统一对照账本

### 关联键与事件

建议以稳定ID串联 signal_id → plan_id/plan_version → review_id → proposal_id → order_intent_id → broker_order_id → fill_id → trade_id。它们不能混用：一个交易可以包含部分成交和多次退出提案，broker_order_id也不能用proposal_id冒充。

signal_id应由账户作用域、标的、策略版本、信号K线结束时间及信号类型确定，重启重复扫描不产生新机会样本。trade_id标识一次从首次成交到全部平仓的交易周期。

每个事件带 event_id、event_type、account_scope、schema_version、event_time、observed_at、payload_hash及关联ID。记录包含但不限于：

| 事件 | 写入时点 |
| --- | --- |
| rule_candidate / rule_rejected | 规则结果确定时，LLM调用之前；保存全部进入约定候选集合的结果 |
| evidence_snapshot | 输入资料冻结时，保留当时可得版本 |
| plan_created / plan_revised | 初稿或修订生成，旧版本不可覆盖 |
| llm_requested / llm_completed / llm_failed | 请求、返回、解析失败、超时、过期分别记录 |
| proposal_created / human_decision / proposal_expired | 展示、批准、拒绝、覆盖理由及未操作结果 |
| order_submitted / order_unknown / order_rejected | 以执行入口和券商对账状态为准 |
| fill_received / fee_adjusted | 实际成交与费用修订，支持重复回报幂等 |
| position_reviewed / trade_closed | 持仓事件复核、确认全部平仓后的结果 |
| outcome_marked | 未交易机会及未平仓交易的约定时点估值，与真实盈亏分开 |

### 落盘与恢复

建议在已有SQLite数据库增加版本化表，不新建另一份可能与真实持仓冲突的权威仓位账本。原始证据可按哈希保存，数据库存索引。现有JSONL保留兼容和导出用途，不再作为唯一关联基础。

订单状态、成交更新与待导出事件在同一事务写入outbox，由后台幂等投递至分析账本。导出失败记录队列积压并重试，不能再次下单。记录不可覆盖；费用更正、迟到资料和人工修订追加新事件。

必须区分两种故障：分析报表或JSONL导出失败不阻塞已批准订单；计划/批准凭据等必要持久化失败时不能产生新的买卖订单。任何降级都不能绕过当前执行保护或制造重复提交。旧库先备份并做迁移验证，不推测补写历史批准或LLM结果。

### 成交与R的统一口径

保存报价时的计划风险R、实际入场成交建立的初始风险R0，以及剩余持仓风险三种不同数据。R0在入场订单全部终结、累计入场数量确认后按确定规则冻结；入场订单仍未终结的交易只显示暂定风险，不混入最终R统计。之后跟踪止损抬高或部分卖出都不重写整个交易周期的R0。后续费用修订追加事件。

净盈亏用真实成交价格、数量、费用和方向计算，不能用触发价代替成交价。累计成交回报转换为增量时，同时用累计成交金额差计算该增量金额；不能把最新累计均价直接当作新增部分的成交价。券商有独立成交ID时优先使用；否则采用订单ID与累计成交数量等组成幂等键，并验证金额异常。

未知初始风险的历史仓位仍展示实际金额盈亏，但R指标为不可计算，不能用默认5%补造。未平仓、部分平仓和完整平仓分别报告。

## 八 如何判断LLM是否有贡献

以同一组规则候选、相同数据可得时间、风险预算和成本假设构建对照。对照结果是条件模拟，不自动等于因果贡献。

| 层次 | 定义 | 主要回答的问题 |
| --- | --- | --- |
| A 规则基线 | 约定候选全部进入同一组合模拟，使用冻结的规则退出，不让LLM和人工结果影响它 | 原规则在相同资金约束下表现如何 |
| B 规则加LLM | 同一候选集合，根据当时已保存的LLM推荐采取预先定义动作，其他规则不变 | LLM筛选或退出建议是否带来增量 |
| C 规则加LLM加人工 | 按真实人工选择和确认时间，在同一模拟执行器中重放 | 人工筛选及等待如何影响结果 |
| D 实际成交 | 使用真实成交、费用、未成交和订单生命周期 | 与可比模拟相比，实际执行损耗多少 |

主对照中的A/B使用相同决策时钟，以隔离选择差异；另设“规则信号立即执行”的时钟敏感性实验，单独评估等待LLM带来的代价。LLM失败或缺失单列失败组，不能从总体样本中删除。

入场和退出分别实验：检验买入建议时固定退出规则；检验退出建议时固定入场集合和初始风险。暂缓建议必须预先规定复核时间及后续处理，没有明确规则则单列观察，不事后挑最有利价格。减仓尚无受测执行政策时，不擅自按50%回放。

先输出单信号的1/3/5个交易日前向收益、最大有利/不利变动与模拟R；再输出受现金、持仓数、产业链和挂单约束的账户重放。单信号收益不能简单相加冒充组合收益。时点选择只是评估口径，需在实验开始前固定并版本化。

报告至少包含：各层净期望R、净盈亏、账户回撤、持有时间、利润集中度、样本数、LLM失败率、人工批准率、未成交率，以及LLM耗时、人工等待、提交到成交耗时。LLM费用单独列示，并给出扣除它之后的结果。

拒绝后上涨不直接等于错误，批准后亏损也不直接等于失误；必须对照当时风险、原计划与共同评估窗口。报告模型反对而人工执行、模型支持而人工拒绝等交叉组，并提示这些组的选择偏差。

参数与提示词变更记录到experiment_id。按时间划分训练、验证及锁定样本外区间；跨边界持仓采用预先约定的隔离或结算规则，防止结果泄漏。按策略、市场阶段和产业链分层，并用日期分块等方式评估不确定性，不能把同一天相关股票视为独立样本。样本不足时写“暂无法判断”，不宣布LLM已经提高收益。

## 十 验收与运行约束

工程测试必须使用合成行情和模拟券商，不自动连接实盘。至少验证以下情形：

1. 规则通过但LLM失败、用户未操作或订单未成交，都留有完整终态或待处理状态。
2. 重启重复扫描、重复模型回调、重复成交回报不会产生重复机会、重复盈亏或重复订单。
3. 部分成交和部分撤单的真实金额、费用、剩余仓位、R0与剩余风险相互一致。
4. 用户批准后计划被修订、报价过期或出现重大新事件，旧批准不能用于新版本执行；已提交订单不因模型回调自动撤改。
5. 新闻含指令、来源缺失、事实引用不存在、模型输出格式异常或资料不足，不能伪装成有效建议。
6. UTC/美东转换、夏令时、日线/15分钟周期及当时可得时间均可重放，无未完成K线或未来新闻泄漏。
7. 审批超时、模型不可用、用户拒绝和模型反对均不触发未授权买卖；模型反对后用户覆盖必须可追溯。
8. SQLite事务与outbox故障注入验证不丢关键状态；导出重试不重复执行交易。
9. 同一数据和同一实验版本重复运行，报告结果一致；受资金约束的A/B/C/D不能靠简单平均收益替代。
10. 所有新增组件关闭后，系统仍保留现有LLM加人工审批、风险预算与对账流程，不降级成自动下单。

启动频率、优先队列并发、模型超时和成本预算先设为显式可配置参数，通过离线回放与影子运行测量，不提前承诺吞吐或响应秒数。硬止损待评估时可优先处理和提示；超时仍不绕过用户要求的审批。

## 十一 首批交付清单

首批开发按以下顺序进行：确定事件schema和关联ID；补齐扫描到真实成交的端到端写入；实现一页交易计划和输入快照；接入买入/卖出的结构化LLM评估；在确认页显示版本、依据和用户覆盖理由；输出第一份候选到成交的对照报告。

首批不新增自动加仓、自动降仓、复杂多模型投票或模型自改参数。持仓事件复核在账本可验证之后接入。先把每次建议变成能追溯、能比较的决定，再根据样本外结果决定是否扩大LLM的作用。
