| # | 问题 | 修复 |

| ① | 次日执行的机会被当天开盘成交（前视） | `run-forward` 重构为「计划日入队、到期认领」；`step()` 顶部加**整批**执行日守卫（先于任何状态变更、一次报出全部违规）；LLM 决策移到**信号日 t 收盘后** |

## 3. 按最小落地设计推进（第一批：证据与候选）

### 3.1 修一处与设计冲突的实现：`DATA_BLOCKED` 的适用范围

设计 §5.3/§6 规定 `DATA_BLOCKED` 是**机会级**判定，必须**同时**禁止 R 与 L 的新风险。
原先只在 L 侧剔除，**R 仍会照常买入**。改为两阶段：

- `freeze_entry_reviews`（账户无关）：一个机会一个冻结证据包 + 数据质量分流；
- `record_data_blocked`：机会终态 + 每个账户一条禁止新风险的账目；
- `apply_entry_reviews`（仅 L）：对已冻结的包做三态评审。

`run-session` 与 `run-forward` 走同一套（设计 §7 要求共同编排）。

### 3.2 机会字段与证据包契约

- `Opportunity` 增 `parent_strategy_id` / `signal_generated_at` / `decision_deadline` /
  `rule_reason_codes` / `market_snapshot_id`（设计 §4：模型不自行计算 ATR/下单量/止损）。
- 证据包增 `identity`（防同名公司事件误配）/ `rule_plan` / `market_context`（含 `price_unit`）/
  `provenance`；事件增 `excerpt` / `source_url` / `event_type` / `cluster_id`；`rule_plan` 无效计入 BLOCK。
- 证据**等级**（strict/diagnostic）冻结进包与账本：诊断级证据上的 VETO 与严格级上的不是同一个东西。
- `put_opportunity` 改**首次写入即冻结**（墙钟字段每次重跑都不同，改写会直接撞「同 event_id 异 payload」）。

### 3.3 修一处 `as_of` 语义偏差

设计 §3 里有**三个**不同时刻，原先把前两个揉成了一个：

| | 定义 | 实现 |
|---|---|---|
| §3.1 | 行情/规则输入截止 = 信号日**收盘** | `entry_market_cutoff` |
| §3.2 | 证据 as_of = **实际采集时刻** | `entry_collection_time` + `validate_evidence_cutoff` |
| §3.3 | 决策截止 = 执行日开盘前 10 分钟 | `entry_response_deadline` |

原实现用收盘做 as_of，会把**盘后发布的事件**（正是财报最常发布的时段）**系统性排除**。
校验不夹紧：早于收盘或晚于截止都直接拒绝（夹紧会把「其实晚到了」伪装成「当时就看到了」）。

同时补上设计 §7 的持久化要求：新增 `shadow_packets`（PK 为
`(experiment_id, opportunity_id)`，天然保证「同一机会只有一个冻结证据包」）+ `shadow:packet`
事件；包**首次写入即冻结**、重跑原样复用；完整包整体落库（§7 明令「不能只保存 packet_hash
及最终动作」）。

### 3.4 证据来源适配器（`evidence_source.py`）

设计 §5.2：接口 `load_events(security_id, cutoff) -> EvidenceFetchResult`。

**核心条款**：`observed_at` 是**系统实际入库时间**，不由导入文件追溯指定 —— 点对点可得性
要证明的是「我们当时确实看得到」，这件事只有采集管道知道；文件说的时间是它的自述。因此
导入与读取分成两步（`import_evidence_jsonl` 在入库那一刻写死），否则重跑会让证据随重跑而
「变得可得」。窗口/容量固定在 manifest；容量截断记进 `exclusion_reasons` 不静默；采集失败
返回 `FAILED` 而不是空事件。

**关键成果：严格模式（strict）由此变得可达。** 现有 futu 盈利日历源 `observed_at` 100% 缺失，
严格模式下 500/500 包为空、模型永远不会被调用；走导入路径后事件带真实入库时间。

## 4. 第二批：共同编排与决策/结算分离

### 4.1 `entry_review.py`（设计 §7）

- `decision_id` 绑定 experiment / scope / opportunity / **packet_hash** / 模型 / prompt 版本 /
  schema 版本：任一变化都是**另一个问题**。重跑时若同一机会上已冻结的 decision_id 不同，
  报 `PACKET_CHANGED_ON_RERUN`——不复用（答非所问）、也不重算（用今天的信息改写当时的依据）。
- 状态机 PREPARED → CALL_STARTED → COMPLETED/FAILED/TIMED_OUT/UNKNOWN，最终动作另存 FROZEN。
- 复用 `shadow_job_runs`（设计 §7 明说要「复用现有 attempt 存储能力」），`fencing_token` 即租约。
- 原子领取 `BEGIN IMMEDIATE`，**网络调用在事务结束之后**。
- 领取结果严格四分：`claimed` / `already_started` / `abandoned` / `finalized`。
- `Application.applied` 拆成 `decision_frozen` / `execution_applied`：**冻结 ≠ 成交**。

### 4.2 CLI 三命令分离（设计 §9）

| 命令 | 能做什么 | 结构上做不到什么 |
|---|---|---|
| `prepare-entry-reviews --session T` | 只用截至 T 的输入生成机会、冻结证据包 | 不要求已有 T+1 行情 |
| `review-entries --execution-session T1` | **唯一**调用模型的命令 | 要求包已冻结，不能临时现造 |
| `settle-session --session T1` | 消费冻结动作 + 当日行情推进 R/L | **没有模型**，读不到当天结果后补作决策 |

`run-forward` 现**拒绝** `use_real_model`——它是历史重放工具，过去的执行日不能用今天生成的
结果补填（§9 明写）。

## 5. 第三批：报告与受控真实调用

### 5.1 报告（设计 §8）

- `entry_metrics`：有效真实评审覆盖率 / 实际交易计划改变率 / 决策到执行可追踪完成率。
  **分母为 0 时返回 None 而不是 0**（「没有对象可评」≠「评了但全放行」）；
  「有效真实评审」要求真实模型 + 确实发起调用 + 拿到输出 ⇒ **夹具评审绝不计入覆盖率**。
- `decision_trace` / `render_trace`：逐项展示规则原计划、证据摘要与链接、模型原始动作、
  最终动作、降级原因、执行结果、费用与「成本未知待补记」。

### 5.2 第一次真实模型调用（设计 §12 + §9）

按 §9 的 `historical_debug` 出口实现并执行：真实调用、完整留痕，但**不写 Application**——
一旦落成账目，过去的执行日就相当于用今天生成的结果补填前瞻记录。

DeepSeek `deepseek-chat`，标的 SEC-US-MU（信号 2026-09-03，pullback + 周线上行 + 市场门开）：

> 「证据包为空：events 为空、evidence_mode 为 strict 且 fundamentals 为空，没有任何可引用的
> 证据……按规则证据不足时采用父策略，不否决。」

模型正确读懂了包的元数据。校验零错误。且严格做到：`applications_written: 0`、正式账本未被
触碰、三项指标如实排除它（`real_model_reviews: 0`）、成本如实记为**未知**（不记成免费）。

**但它证明的范围有限，不应被读大**：这次调用跑在**空证据包**上，按设计 §12 自己的话，
「模型 API 成功响应**仅验调用**」——它验证的是调用链路可用，**不是**"真实证据驱动的模拟交易
闭环"，也不是模型判断力的价值。后者见 §7（有真实证据，但用的是确定性 fixture 模型）。
**两者尚未合并成一次「真实证据 + 真实模型 + 模拟结算」的运行**，那需要一次实时窗口。

## 6. 测试抓出的真 bug（本日最有价值的部分）

这些都不是靠读代码发现的，是**把不变量写成可测的断言**逼出来的。单看代码每一处都「看着对」。

| # | Bug | 代价 |
|---|---|---|
| 1 | `prepare_review` 用 `INSERT OR REPLACE` 登记，**把 CALL_STARTED 连同租约一起抹掉** | 重启后的接管者以为自己是首次调用——崩溃证据被「登记」这一步自己销毁 |
| 2 | 租约判据最初拿「新租约」而非 `now` 作比较基准 | 见 #10 —— 这一条我**第一次修错了**，改成了另一个同样错误的比较 |
| 3 | `mark_execution_applied` 只更新投影列、没更新 body，而 `application()` 读的是 body | 两者不一致，`execution_applied` 永远是 False |
| 4 | R 侧无 Application 导致 `_mark_applied` 报 `APPLICATION_MISSING` | 结算中断；按 §6 应补 `INTENT_CREATED` |
| 5 | **两套状态词汇没对齐**：`call_model` 返回模型侧 `'OK'`，状态机取值是 `COMPLETED/...` | `'OK'` 不是终态 ⇒ **成功的尝试被当成从未终结**，重跑时按崩溃遗留覆盖成 UNKNOWN，**把已付费的有效结果冲掉了**（第一次真实调用的留痕就这么丢过一次）。非 debug 路径同样中招 |
| 6 | `float('nan')` 是 **truthy** 的，`str(raw.get(k) or '')` 把 pandas 缺失字段变成字面量 `'nan'` 混进 prompt；NaN 又让包 JSON 落库失败 | 缺失值伪装成内容 |
| 7 | `evidence_store.select_visible` 按诊断策略放行后，`evidence._norm_events` 又**无条件要求两个时间戳**把它们全丢掉 | **诊断模式完全失效**（1302 条记录里 AAPL 的 50 条 → 0 事件） |
| 8 | `market_close` 返回 pandas `Timestamp` 直接进 `Application.as_of` | JSON 序列化崩溃 |
| 9 | 过滤被否决机会时遍历了**所有**执行日的队列 | 误删其它交易日的待执行机会 |
| 10 | **租约比较错误**：判据写成「旧租约到期 > now + 新租期」（等价于拿本次开始时刻与 now 比），而非「> now」 | 租约远未到期时把正常调用判为崩溃遗留 → **提前冻结 ABSTAIN**，并与仍在飞行的 worker 的有效结果冲突。**这是我上一轮"修复" `>`→`>=` 时自己引入的**，且被「同一时刻领两次」的测试恰好掩住 |
| 11 | **VETO 的模型成本完全漏记**：结算时 `continue` 发生在成本累加之前 | 否决越多、漏算越多（违反 §8「L 承担所有模型调用成本，包含失败和弃权」） |
| 12 | **未完成评审时 L 静默跳过买入**（R 仍按规则买入） | 调度失败或调用崩溃，在账户结果上表现成一次**没有记录的"否决"** |
| 13 | 成交状态与 `execution_applied` **不是原子提交**（先 `save_state` 再 `_mark_applied`） | 两步之间崩溃 → 账户已成交而标记未写；重跑 `step` 返回 no-op 直接跳过，**缺口再也补不上** |
| 14 | fixture 的 `--fixture-action VETO` 没有引用包内证据 | 被验证器降级成 `INVALID_OUTPUT`→ABSTAIN，**L 反而买了**（设计 §11 的确定性 VETO 验收案例因此失效） |
| 15 | `settle-session` 没有收口机会终态（`run-forward` 有） | 漏斗终态停在 READY，配对绩效的「明确失败终态」判定随之失真 |

## 7. 有真实事件证据的验收：决策 → 模拟结算 → 重启重跑

按用户要求做的一次完整验收（实验 `M1-ACCEPT-20260917`）。

**证据是真实的**：从 `data/evidence_runs/futu-earnings-20260912/evidence.csv` 取 SEC-US-MU
的事件（50 条），用 `import-evidence --observed-at-policy unknown` 导入 —— 该源**本来就没有**
首次观测时间，如实留空胜过伪造一个时间戳（这类记录只在诊断模式下可用；严格模式要求
`observed_at`，正是为了逼出「我们当时是否真的看得到」这个问题）。

链路与结果：

```
① prepare-entry-reviews --session 2026-09-03 --evidence <真实事件>
   → 包质量 OK（此前空证据时是 LLM_INSUFFICIENT），含 1 条真实事件：
     2026-06-24 MU 财报（futu://earnings_price_move，published_at 可追）
② review-entries --execution-session 2026-09-04 --model fixture --fixture-action VETO
   → 确定性 VETO（设计 §11 验收案例），引用包内 evidence_id
③ settle-session --session 2026-09-04
④ 重启重跑 ①②③ 各再跑一次
```

| 验收点 | 结果 |
|---|---|
| R 按规则买入 | `INTENT_CREATED`，现金 92,221.55，持仓 `[SEC-US-MU]` |
| **L 不买入** | `VETO/MATERIAL_COMPANY_EVENT_RISK`，现金 100,000.00，**无持仓** |
| 入场成交事件数 | 1（只有 R）—— 未出现重复成交 |
| 冻结 ≠ 成交 | L `冻结=True 成交=False`；R 两者皆 True |
| 机会终态 | `EXECUTED`（R 成交了；L 被否决是账户级细节，不改变共享漏斗终态） |
| 重启重跑 | 三命令结果稳定，`intents_applied` 不增；账户不重复推进 |
| 三项指标 | 实际交易计划改变率 **1.0**（1 改变 / 1 评审）；有效真实评审覆盖率 0.0（夹具不计入）；可追踪完成率 `None`（L 侧无「已批准应用」可统计） |
| 决策追踪 | 规则原计划 / 真实证据与来源链接 / 模型动作 / 最终动作 / 执行结果 / 费用，六项齐全 |

**这次验收暴露了 #14 与 #15 两个真 bug**（见 §6），修完之后才得到上表结果。
