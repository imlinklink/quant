# 下一步优化与编码路线

更新时间：2026-09-08。面向当前 quant_us-main 实现，供独立编码和后续验收使用。

## 1. 先明确目标

现阶段优先解决“系统为什么没有动作、发生异常后如何定位、券商状态如何可靠恢复”，随后再研究 LLM 是否改善决策。暂缓新增策略和调整买卖阈值，并不意味着停止开发：可以先做可观测性、数据质量和隔离联调工具。

建议第一个提交做 **决策状态面板与明确的阻塞原因**，第二个提交做 **建议池时效与来源标记**。两项都不需要等待市场出现交易信号，也不改变订单行为。

## 3. 推荐开发顺序

### 任务 A：让用户看懂系统为何没有动作（优先做）

**问题：** “LLM 已启用”不代表调用成功；确认页为空既可能是没有合格信号，也可能是资料不足、评估失败或过期。目前漏斗行中规则拒绝仍可能显示 human=unhandled/outcome=unhandled，容易被误读为漏处理。

涉及文件：

- web/app.py：/api/approvals、/api/decision-report；可新增只读 /api/decision-health。
- web/templates/approvals.html：状态摘要、空状态与提案卡片。
- scripts/live_trading/decision_ledger/funnel_report.py：逐信号状态及分母口径。
- scripts/live_trading/decision_ledger/workflow.py：模型排队和调用阶段。
- scripts/live_trading/approval/proposal_store.py：评估状态、批准前提。

实现要求：

1. 分开显示“配置启用”“最近请求时间”“最近成功时间”“最近失败原因”；没有调用过应显示“尚未调用”，不显示“连接正常”。
2. 显示最近扫描时间、规则通过/拒绝数量、提案数量、评估中数量及到期时间。扫描时间必须来自实际扫描完成或独立心跳；重复信号去重后的事件时间不能冒充最新扫描时间。
3. 把不可批准原因做成稳定的原因码，例如 review_pending、review_failed、insufficient_information、review_expired、plan_changed、proposal_expired，前端映射中文。以上是建议新增字段，不是现有 API 承诺。
4. 提案状态、评估状态和批准资格分别保留；llm_ready=true 也不能代表订单已满足所有执行条件。执行时继续核对行情、账户、风险预算和批准绑定。
5. 漏斗中，没有提案的规则拒绝显示“规则未通过”；没有合格信号不统计为模型失败。明确“扫描样本”“规则通过样本”“已创建提案”三个分母。
6. 按账户作用域统计；日志和接口不暴露 API key、授权头或完整请求凭证。获取状态不得触发 LLM 请求、批准或下单。

验收用例：

| 输入场景 | 预期结果 |
| --- | --- |
| 7 条规则拒绝、没有提案 | 显示“无符合条件信号”，模型请求数为 0 |
| 已配置 LLM，但没有请求 | 显示“尚未调用” |
| 请求超时或 schema 校验失败 | 保留失败记录，给出可识别原因，不能批准 |
| 模型返回资料不足 | 显示资料缺口，不归为网络故障 |
| 计划修订后旧评估返回 | 旧评估不恢复批准资格 |
| 两个模拟账户有记录 | 当前账户面板不混入另一个账户 |

建议扩展 tests/unit/live/test_decision_workflow.py；漏斗增加独立测试，验证规则拒绝与“有提案但人工未处理”的区别。

### 任务 B：建议池显示时效与来源

**问题：** 历史研究建议容易被当作实时信号。建议池的外部报告内容也不能直接当成已核实交易证据。

涉及文件：scripts/live_trading/llm_suggestions/store.py、report_reader.py、picker.py，web/app.py 的 /api/suggestions，以及 web/templates/suggestions.html。

实现要求：

1. 新生成记录统一写带时区的 generated_at；保留来源报告时间和取得时间。旧记录时间没有时区时标记“时区未知”，不要默认为 UTC。
2. 页面同时显示生成时间、来源时间、距今时间和 freshness 状态。时效阈值可配置；来源时间缺失、未来时间或无效时间单独处理。
3. 陈旧建议仍可查看、忽略或加入观察池；加入观察池后必须重新经过当前策略扫描、证据取得和计划评估，不能复用旧建议授权订单。
4. 区分“报告中的说法”和“已核实数据”。报告生成时间新，不等于它引用的行情或新闻也新。
5. 如修改存储，顺带采用临时文件加原子替换，避免写入中断留下半个 JSON；多进程更新须处理覆盖冲突。不要让 GET 接口自动刷新模型。

验收：覆盖有时区新记录、无时区旧记录、陈旧来源、新生成但旧来源、未来时间、损坏 JSON。加入观察池不创建批准记录或订单。

### 任务 C：把模拟联调做成可复跑的工具

**目标：** 用一致的步骤留下证据，而不是靠目测日志认定系统可靠。

涉及文件：scripts/live_trading/preflight_check.py、run_all.py、execution.py，以及 tests/unit/live/test_broker_execution.py、test_deployment_acceptance.py。

建议新增 scripts/run_simulate_acceptance.py；分成只读检查和需要人工操作的订单验证步骤：

1. 默认只读：检查 SIMULATE、账户唯一性、行情时间与可用性、确认页、数据库作用域、LLM 最近状态。输出脱敏 JSON 报告。
2. 脚本不自动点击批准或伪造策略通过；真实策略闭环等待有效提案，由人确认。若另做券商协议测试，必须明确标记合成测试，隔离账户/账本并排除出策略表现统计。
3. 为一次闭环记录 signal_id、plan_id/version、review_id、proposal_id、order_intent_id、broker_order_id、trade_id，以及各阶段时间。
4. 核对提交、成交、卖出或撤单、重启恢复。启动前记录 PID 和端口，避免第二个监控进程重复运行；只停止自己启动的进程。
5. 模拟券商不一定能稳定制造部分成交、提交响应丢失等情况。这些继续使用 mock 故障注入，报告中分开标注“真实 SIMULATE 验证”“mock 验证”“未覆盖”。

必须验证的结果：

- 一个批准最多创建一个订单意图；超时后先查询，不通过重试提交解决 unknown。
- 部分成交数量、均价、剩余挂单和持仓一致，重复回报不重复计入。
- 重启恢复同一账户的状态；不能把查询失败当作零持仓。
- 不同状态显示准确：DRY-RUN 是本地不向券商下单，SIMULATE 是券商模拟账户，REAL 是真实账户。清理监控器中把 dry_run=false 一概写成“实盘”的日志。
- 预检中不要把 accinfo 查询成功等同于 REAL 账户已解锁；查询权限与下单权限分开描述。

通过条件：至少有一笔真实模拟账户闭环和一次恢复核对报告；未自然触发的故障路径有离线测试，并明确剩余限制。服务返回 HTTP 200 不算订单闭环完成。

### 任务 D：成交更正与费用补齐（闭环后再做）

**现状：** 累计成交增量、费用修订、R0 冻结已有实现。当前遇到终结订单后新增成交会拒绝静默更新，需要明确的更正流程；券商适配器尚未保证返回实际费用。

涉及文件：execution.py、position_registry.py、decision_ledger/event_store.py、funnel_report.py。

实现要求：

1. 先留存脱敏的真实券商字段样例，再写适配器；缺失费用保持未知，不能用成本预算冒充实际费用。
2. 为券商成交更正设计独立追加事件和幂等键，保留原记录。不能只删除“终结订单新增成交”的报错保护。
3. 若更正入场数量/金额影响 R0，保留原始冻结值，新增更正版本及受影响交易统计；普通止损上移仍不能重写初始 R0。
4. 发现差异时进入明确的待核对状态并提示，限制受影响订单/标的继续执行；不要静默修成表面一致。解除限制应有可审计条件。
5. 费用和数量更正、持仓更新与事件追加必须事务一致。

验收：重复成交回报、累计数量倒退、终结后新增成交、费用缺失后补齐、费用上调再下调、费用退款、历史成本未知、事务失败回滚。每个事件重复回放都不改变最终结果。

### 任务 E：补证据，再评估 LLM 效果

完成 A–D 后，按以下顺序开展，不要一次同时改模型、提示词和策略阈值。

1. **输入质量：** 统计真实提案最常缺的资料，按缺口补价格时间、成交量、止损、收益风险比、财报/公告等。补充独立来源与取得时间，不靠提示词要求模型更积极来减少“资料不足”。
2. **重大事件：** 对接已有 register_material_event；区分重复报道与新事件，绑定来源和账户/标的。自动订阅完成前，不声称系统已覆盖所有财报公告。
3. **影子复核：** 复用 position_review.py，默认关闭，先只记录结果；不要赋予修改止损、加仓或直接卖出的权限。
4. **离线实验：** 扩展 decision_ledger/comparison.py，固定策略版本、候选集合、公共决策时钟、资金约束、费用/滑点假设。分别比较纯规则、规则加 LLM、人工确认流程和实际成交。
5. **样本外：** 事先按日期划分训练、验证、锁定测试期；同日或重叠持仓不能当独立样本随机打散。阈值与提示词只在训练/验证期修改。
6. **报告：** 同时展示样本量、拒绝/资料不足/超时占比、费用覆盖率、净 R、回撤与区间不确定性。不要把单次成功请求、模型信心或少量盈利交易当作有效性证明。

## 4. 暂时不要改的内容

- 不为“尽快看到订单”降低入场阈值、放宽行情时效或延长审批有效期。
- 不取消人工确认、价格偏离限制、证据校验或 unknown 订单保护。
- 不把资料不足改成允许执行，不把缺费用改成零费用。
- 不把研究建议直接接到订单入口，不让模型自行改数量、止损或风险预算。
- 不重建一套数据库/事件系统，也不重复开发已经通过测试的计划版本绑定。
- 不修改运行数据库来制造演练记录；不要边改代码边假定已运行进程自动加载新版本。

## 5. 每个提交怎样交付

建议拆成独立提交：A 状态与原因 → B 时效与来源 → C 联调工具 → D 更正与费用 → E 数据与实验。完成前两项即可先停下来做模拟账户验收，不必等整份路线全部完成。

每项完成时记录：具体问题、行为变化、测试结果、是否需要重启、未覆盖边界。开发使用独立分支，例如 codex/decision-observability；保持当前联调配置为 SIMULATE，账户与密钥不提交。

项目根目录可执行：

```sh
# 决策链路针对性回归
python3 -m pytest tests/unit/live/test_decision_workflow.py -q

# 执行与恢复回归（临时库、mock 券商）
python3 -m pytest tests/unit/live/test_broker_execution.py tests/unit/live/test_deployment_acceptance.py -q

# 改动影响公共状态或执行层时，运行完整单元测试
python3 -m pytest tests/unit -q
```

上述测试不替代真实 SIMULATE 验收。不要在测试中导入启动入口并启动监控，也不要向正在运行的 /api/approvals 写入合成提案。

## 6. 可以直接作为首个编码任务的说明

> 在不改变交易策略、批准规则和下单行为的前提下，完善 quant_us-main 的决策可观测性。新增只读状态摘要，区分 LLM 配置启用、尚未调用、成功、失败和资料不足；确认页展示不可批准原因及最近实际扫描时间。修正漏斗行把无提案的规则拒绝显示为人工未处理的问题，保留按账户隔离和原有事件去重。为规则拒绝、未调用、评估超时、资料不足、评估过期、计划修订和账户隔离添加回归测试。不要调整买卖阈值，不调用真实订单接口，不向运行数据库写入测试数据。
