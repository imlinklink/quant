## 3. 修掉的一处正在发生的生产故障（结算链路）

**现象**：`live_trading/run_outcomes.py` 自 2026-09-19 11:29 起连续 `exit=1`：
```
{"status":"settlement_conflict","reason_code":"event_conflict","retryable": false}
```

**根因**（副本复现抓到确切差异）：
```
分歧行 1：VALUE_DIVERGED 1d research_batch_01ce7a1 delta=1.2803993976184813e-13
```
`excess_return_pct` 两次运行差 **1.28e-13**，而 `return_pct` **完全相同** ⇒ 个股收盘序列
一致，**基准（SPY）序列每次重取、浮点末位不同**。事件键固定 ⇒ `insert_event` 抛
「同一事件ID出现冲突内容」⇒ `retryable: false` ⇒ **日结算永久失败、永不重试**。
**一个没人会看的浮点末位把整条链路钉死了。**

**修复**：
1. **防重算（主）**：已结算的期限跳过。判据是**事件是否存在**，不是"投影说 `good`" ——
   该函数先在事务 A 写投影、再在事务 B 写事件；中间失败会留下"投影 good 但事件缺失"，
   跳过它就等于让账本永远缺这条记录。
2. **量化（辅）**：落库指标量化到 1e-6。
3. **显式修订** `revise_outcome`：唯一能改写已记录结果的入口，**不复用原事件键**（`rev{n}`），
   载荷带 `previous`/`reason`/`operator`，须人工调用。
4. **投影不一致的核查与修复**：`divergences()` 报出，`repair_projection` 只修 ≤1e-6 的
   （更大的**拒绝**并要求走 `revise_outcome`），修复留 `outcome_projection_repaired` 事件，
   **不动 `outcome_observed`**。
5. 顺带修正 `settled` 计数语义：原先数"算出了多少"（重跑也报 10 条），改为数"真写入了多少"。

**恢复方式（你要求查明的）**：`run_outcomes.main()` 失败**不持久化任何状态**；
服务侧 `ShadowJobs.execute` 的键是 `(job_key, 日期)` ⇒ **次日自动重新领取，无需清理**。
需处理的只有两件：① 那一条投影不一致的行（用 `repair_projection` 修）；
② 冲突处**整批中止**，那天之后的条目会在下次成功运行时补齐。**失败记录全部保留**。

### 6.1 复核四个验收修复时又发现的两处（已修）

你对上述问题做了四项修复后，我逐项复核（**结论：四项的实质内容都正确**，并在副本上
独立复现了 1257 passed 与 `git diff --check`），复核中发现两处新问题：

| 问题 | 性质 | 处置 |
|---|---|---|
| `ALREADY_HELD` 会触发 `consult_required=True` | **由"持仓计入"那项修复带出的副作用**：`conflict = any(reason != 'INSUFFICIENT_CASH')`，而 `ALREADY_HELD` 是新增的拒绝原因。后果是——一个**已持有**的标的再次成为候选时会发起一次**付费模型评审**，而 Portfolio 在那情形下**无可决策**（所有模板都会同样拒绝它，换序也改变不了什么）。这正是 §6.3「没有容量冲突时默认不调用」要避免的 | 把 `ALREADY_HELD` 与 `INSUFFICIENT_CASH` 一并列入 `NON_CONTESTING_REJECTIONS` |
